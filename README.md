# ARGUS · Підсистема відображення повітряної обстановки над акваторією та узбережжям

Курсова робота на тему **«Підсистема відображення повітряної обстановки над акваторією та узбережжям системи моніторингу морських і повітряних цілей ARGUS»**.

Повний програмний продукт: операторська картина в реальному часі, зони контролю, журнал тривог, статична карта акваторії/узбережжя, автономний демо-режим, 54 модульних тести, каталог компонентів і повна навчальна документація.

## Коротко про проєкт

### Предметна область

Система ARGUS об'єднує дані радіолокаційних станцій, ADS-B та AIS в єдину оперативну картину. Об'єкт цієї курсової — **кінцева ланка**: підсистема, яка перетворює потік сирих треків на зрозуміле візуальне подання для оператора.

### Що вміє

| Можливість | Реалізація |
|---|---|
| Оперативна картина | SVG-схема: суша, берегова лінія, сітка, кільця 2/5/10 NM, OP-1 |
| Цілі в реальному часі | REST-знімок + WebSocket (або мок-симуляція кожні 5 с) |
| Класифікація | 5 станів належності × 7 класів цілей, кольори та гліфи |
| Геометрія | Haversine-відстань, пеленг, 16 компасних секторів, FL |
| Стани цілі | `fresh` / `stale` (≥90 с) / `lost` (≥240 с) |
| Фільтри | Усі / Повітряні / Надводні / Тривоги — і список, і мапа |
| Картка цілі | Координати, висота, швидкість, курс, пеленг, джерело, впевненість |
| Зони контролю | 4 типи; створення через форму з валідацією полігона |
| Журнал тривог | Подія входу цілі в зону, один раз на пару «ціль–зона» |
| Доступність | Семантика, `aria-*`, клавіатура, видимий фокус, `prefers-reduced-motion` |

### Візуальний код

- Кольори належності: 🟢 свій · 🔵 нейтральний · 🟡 підозрілий · 🟣 невідомий · 🔴 ворожий.
- Гліфи класів: ✈ літак · ⚙ вертоліт · ◆ БпЛА · ▲ ракета · ▬ корабель · ◄ катер · ▽ ПЧ.
- Рамки на мапі: червона — заборонена зона, жовта — повітряний простір, синя — коридор, бірюзова — зона безпеки.

## Хід виконання роботи

Нижче — повний ланцюг від постановки задачі до готового продукту. Кожен етап має свій артефакт у репозитарії.

### Етап 1. Аналіз предметної області

**Що робилося:** описано контекст ARGUS (зондування → фузія → сховище → відображення → керування), виділено об'єкт розробки, сформовано перелік понять (ціль, належність, акваторія, узбережжя, пост, зона, подія входу) та сформовано функціональні й нефункціональні вимоги.

**Результат:** розділ 1 пояснювальної записки, `docs/01-пояснювальна-записка.md`.

### Етап 2. Формалізація та алгоритми

**Що робилося:**

- Введено формальну модель `t = ⟨id, κ, α, φ, λ, h, v, ψ, s, c, τ⟩` та `z = ⟨id, name, type, Π, e⟩`.
- Виведено формули haversine, початкового пеленга, компасного сектора, проєкції на екран.
- Описано алгоритм «точка в полігоні» (метод променя).
- Сформульовано правило детектування події входу: `k ∈ I₁ ∧ k ∉ I₀ ∧ z.e`.
- Визначено пріоритет сортування: hostile → suspect → unknown → neutral → friendly, далі за дальністю.

**Результат:** розділ 2 пояснювальної записки.

### Етап 3. Проєктування архітектури

**Що робилося:** обрано MVVM-подібний стек з чотирма шарами (інфраструктура → домен → стан → подання). Ухвалено рішення про два store, чисту бізнес-логіку в `lib/`, SVG-карту без зовнішнього картографічного рушія, хеш-навігацію `#zones`.

**Результат:** розділ 3 пояснювальної записки, `DECISIONS.md`, діаграми в `diagrams/`:

- `01-usecase.md` — варіанти використання;
- `02-activity.md` — алгоритм діяльності;
- `03-sequence.md` — послідовність оновлення;
- `04-class.md` — класи домену;
- `05-component.md` — компонентна архітектура;
- `06-state.md` — стани з'єднання та цілі.

### Етап 4. Реалізація інфраструктури

**Що робилося:** створено конфігурацію Vite/Vitest/Ladle, шар `api.js` (REST + мок-режими + обробка помилок), шар `stream.js` (WebSocket із exponential backoff та мок-симуляцією), довідники сектора (`data/area.js`) і демонстраційні набори (`data/mockTargets.js`). Описано контракт інтерфейсів — `docs/02-api-contract.md`.

### Етап 5. Реалізація домену та стану

**Що робилося:** реалізовано чисті модулі `lib/geo.js`, `lib/targets.js`, `lib/zones.js`, `lib/simulation.js`, `lib/format.js`; два MobX store з Computation-властивостями (`items`, `mapItems`, `stats`, `selected`) і захистом від застарілих оновлень за `ts`.

### Етап 6. Реалізація інтерфейсу

**Що робилося:** зібрано 14 компонентів: карта, список цілей, картка, фільтри, статистика, журнал, легенда, форми та списки зон. Стилі побудовані на токенах (`styles/tokens.css`) у «тактичній» темній палітрі.

### Етап 7. Верифікація та виправлення

**Що робилося (реально знайдені й виправлені дефекти):**

1. Неправильні відносні шляхи імпорту в store (`./api.js` → `../api.js`) — модуль не завантажувався.
2. Haversine множив радіани на градусну константу — відстані були занижені ~у 57 разів. Введено `EARTH_RADIUS_NM`.
3. Рівень польоту рахувався з подвійним діленням — `3200 м` давали `FL001` замість `FL105`.
4. Вектор курсу обчислювався через подвійний перерахунок масштабів і виходив за межі екрана. Спрощено до піксельного напрямку.
5. Тести(store) не завантажували дані перед перевіркою Computed — додано `await load()`.

**Результат:** 54/54 тестів проходять, обидві збірки успішні.

## Як запустити та використовувати проєкт

### 1. Встановлення

```bash
cd zahorulko_kursova
npm install
```

Потрібен Node.js 18+ (перевірено на v24.15.0).

### 2. Запуск

```bash
npm run dev
```

Відкрийте **http://localhost:5174**.

### 3. Режими даних

Бекенд ARGUS у навчальному середовищі не запускається, тому за замовчуванням зручно використовувати мок-режим:

| URL | Що побачите |
|---|---|
| `http://localhost:5174/?mock=normal` | 11 цілей (6 повітряних, 5 надводних) і 4 зони, рухома симуляція |
| `http://localhost:5174/?mock=air` | лише повітряні цілі |
| `http://localhost:5174/?mock=surface` | лише надводні цілі |
| `http://localhost:5174/?mock=empty` | порожня картина й стани «немає даних» |
| `http://localhost:5174/?mock=error` | демонстрація помилки каналу |
| `http://localhost:5174/` | живий режим (потрібен сервер на `http://localhost:8090`) |

### 4. Робота з інтерфейсом

**Головний екран «Обстановка»:**

1. Угорі — лічильник часу, назва сектора й індикатор каналу.
2. Чотири плитки статистики: усього / повітряні / надводні / тривожні.
3. Кільця навколо посту `OP-1` позначають 2, 5 і 10 морських миль.
4. Кожна ціль на мапі — це гліф класу, пофарбований за належністю, із вектором курсу, позивним і дальністю.
5. Клацніть будь-яку ціль на мапі або в списку праворуч — під мапою з'явиться **картка цілі** з повними атрибутами. Повторний клік або «Закрити» прибирає картку.
6. Фільтри «Усі цілі / Повітряні / Надводні / Тривоги» змінюють і список, і мапу одночасно.
7. «Журнал тривог» показує події входу в зони: ціль, зона, час, домен. Кнопка «Очистити» скидає журнал.
8. Кнопка «Оновити» повторно виконує запит знімка.

**Екран «Зони»** (кнопка в панелі або хеш `#zones`):

1. Форма: назва (мін. 3 символи), тип зони, полігон у форматі `довгота, широта; …` (мін. 3 точки), прапорець сповіщення про вхід.
2. Валідація відбувається до запиту; помилки показуються біля полів і в `role="alert"`.
3. Після успіху зона з'являється на початку списку з підсвічуванням. У мок-режимі запит не йде — зона отримує `id` виду `zon-local-*`.
4. Список показує код типу, опис, координати полігона й стан сповіщень.

### 5. Команди

```bash
npm run dev            # застосунок, http://localhost:5174
npm run build          # production-збірка → dist/
npm run preview        # перегляд збірки → http://localhost:4174
npm test               # 54 модульні тести
npm run test:watch     # тести у режимі спостереження
npm run stories        # каталог Ladle → http://127.0.0.1:61008
npm run build:stories  # статичний каталог → build/
```

### 6. Інтеграція з реальним бекендом

Створіть `.env` у корені проєкту:

```env
VITE_ARGUS_API=http://localhost:8090
VITE_ARGUS_WS=ws://localhost:8090/ws/situation
```

Формати запитів і відповідей описані в `docs/02-api-contract.md`. Для перевірки контракту без бекенду використовуйте мок-режим.

### 7. Налагодження

У консолі браузера доступний `window.argus`:

```js
window.argus.store.tracks.size        // кількість треків
window.argus.store.alerts.slice()     // журнал тривог
window.argus.zonesStore.zones.slice() // зони
window.argus.store.select('UAV-042')  // вибрати ціль програмно
```

## Як презентувати проєкт на захисті

### Структура виступу (8–10 хвилин)

| Хвилина | Що розказати | Що показати |
|---|---|---|
| 0–1 | Тема, актуальність, об'єкт і мета | Титульний екран, `README.md` |
| 1–2 | Предметна область і вимоги | Розділ 1 записки |

| 4–6 | **Жива демонстрація** (див. сценарій нижче) | Браузер, `/?mock=normal` |
| 6–7 | Тестування й верифікація | `npm test` — 54 тести |
| 7–8 | Висновки й напрямки розвитку | Розділ «Висновки» |

### Сценарій демонстрації (обов'язкові кроки)

1. Відкрийте `http://localhost:5174/?mock=normal`. Дайте 2–3 секунди на завантаження.
2. **Покажіть картину:** берегова лінія, кільця дальності, кольорові цілі, зони. Поясніть кольори за легендою внизу.
3. **Покажіть динаміку:** зачекайте 5 секунд —цілі зрушаться відповідно до курсу й швидкості. Зверніть увагу на індикатор «Канал активний».
4. **Виберіть ціль `MIS-001` (ворожа, червона ▲).** Відкриється картка: висота, FL, курс, пеленг, джерело. Поясніть, чому вона перша в списку (пріоритет належності).
5. **Фільтр «Тривоги»:** у списку залишаться hostile/suspect/unknown; на мапі — те саме. Це доводить синхронність подань.
6. **Журнал тривог:** покажіть подію входу цілі в зону «Альфа». Поясніть правило «один раз на пару ціль–зона».
7. **Перейдіть у «Зони»** (`#zones`). Покажіть 4 зони.
8. **Створіть зону:** введіть назву (наприклад, «Демо-зона»), тип «Заборонена зона», залиште полігон за замовчуванням, натисніть «Створити». З'явиться нова картка з підсвічуванням.
9. **Покажіть валідацію:** очистіть назву, натисніть «Створити» — помилка біля поля. Це доводить клієнтську перевірку до запиту.
10. **Покажіть помилку:** відкрийте `/?mock=error` — стан «Канал даних недоступний» із кнопкою «Повторити».
11. **Завершіть тестами:** у терміналі `npm test` → 54 passed. Покажіть `npm run build` → success.

### Поради для захисту

- Тримайте відкритими дві вкладки: браузер із демо та термінал із тестами.
- Пояснюйте **чому** зроблено так, а не інакше — рішення зафіксовані в `DECISIONS.md`.
- Якщо питають про реальний бекенд — покажіть `docs/02-api-contract.md` і поясніть, що заміна мок-шару на реальний API відбувається через дві змінні оточення.
- Якщо питають про масштабування — згадайте розділення store, чисті функції в `lib/` і те, що nieuwe підсистеми додаються новим store без зміни UI.
- Діаграми в `diagrams/` відкриваються будь-яким Markdown-переглядачем із підтримкою Mermaid (GitHub, GitLab, Obsidian, VS Code).

### Можливі питання й відповіді

| Питання | Відповідь |
|---|---|
| Чому MobX, а не Redux? | Менше boilerplate для двох store; Computed-властивості автоматично перераховують похідні дані. |
| Чому SVG, а не Canvas? | Потрібна інтерактивність елементів (клік по цілі, aria-атрибути). DOM-вузли дають це без додаткового коду. |
| Що станеться, якщо сервер зникне? | REST-знімок покаже помилку й останні відомі дані; WS перепідключується з backoff до 30 с. |
| Як додати новий тип цілі? | Додати запис у `KINDS` у `lib/targets.js` і, за потреби, гліф у легенду. Тести — у `targets.test.js`. |
| Чому хеш, а не роутер? | Екранів два; хеш дає посилання, що переживає перезавантаження, і не додає залежність. |
