# Рішення ·ARGUS курсова робота

## Формат проєкту: вебзастосунок, а не desktop

Тема передбачає операторську картину в реальному часі. Вебстек (React + MobX + SVG) дає:
- крос-платформовість без встановлення;
- просту демонстрацію через браузер і локальний dev-сервер;
- можливість інтегрувати будь-який REST/WS-бекенд через змінні оточення.

Це продовжує конвенцію попередніх практичних робіт (React 18 + Vite + MobX + Vitest + Ladle).

## Два store, а не один

`SituationStore` — високочастотні треки, з'єднання, вибір, фільтр, тривоги.
`ZonesStore` — рідкісна зміна зон і форма створення. Різні життєві цикли й різні стани `loading/error` не повинні змішуватися. `App` читає обидва; компоненти залишаються «чистими» щодо MobX.

## Зв'язок store через колбеки, а не глобальний контекст

`SituationStore` отримує `zonesProvider: () => zonesStore.zones`, а `ZonesStore` — `onZonesChanged: () => situation.syncWithZones()`. Це усуває циклічний імпорт і дає змогу тестувати кожен store окремо. Повноцінний Context був би зайвою інфраструктурою для двох store.

## Чиста логіка в `lib/`

Геометрія, класифікація, валідація та симуляція не залежать від React/MobX. Це дозволило покрити їх юніт-тестами без DOM і мережі, а також використати ті самі функції і в store, і в компонентах, і в тестах.

## Haversine з радіусом у морських милях

Початкова реалізація множила кутову відстань (радіани) на `60.0405` — кількість морських миль у **градусі**, що давало занижені в ~57 разів відстані. Виправлено: `D = δ · 60.0405 · 180/π`. Окремий `NM_PER_DEG_LAT` залишено для обчислень у градусах (симуляція руху, кільця дальності).

## Вектор курсу в піксельному просторі

Спроба обчислити вектор через перерахунок NM у градуси й далі в пікселі дала довжину в рази більшу за екран через подвійне ділення на масштаб. Вектор — це схематичний напрямок, тому обчислюється безпосередньо: `dx = sin(ψ)·L`, `dy = −cos(ψ)·L`. Формула проста й передбачувана.

## Рівень польоту (FL)

FL — це сотні футів, тобто `h[m] / 30.48`. Додаткове ділення на 100 було помилкою (3200 м давали FL001 замість FL105). Виправлено в `altitudeLabel()`.

## Детектування входу в зону через множину ключів

Замість порівняння координат «вчора/сьогодні» використовується множина `id_target:id_zone`. Подія виникає лише при переході «не в зоні → в зоні». Це усуває дублювання повідомлень на кожному русі цілі всередині зони.

## SVG-карта замість картографічного рушія

Завданню достатньо схематичного подання: берегова лінія, суша/вода, кільця дальності, зони, цілі. Використання Leaflet/Mapbox додало б залежність, ключі та мережеві тайли. Проєкція «еквідистантна за широтою» на невеликому секторі (0.55° × 0.25°) дає прийнятну точність.

## Мок-режим як повноцінний шлях демонстрації

Без реального сервера ARGUS перевірити роботу неможливо. `?mock=…` підміняє і REST, і WS, але проходить ті самі функції нормалізації, decoration і валідації. Створення зони локально дає змогу показати повний цикл без бекенду.

## Хеш-навігація `#zones`

Два екрани в межах одного застосунку. Хеш дає посилання, що переживає перезавантаження, і працює зі статичною збіркою `base: './'`. Роутер буде додано лише за появи третього екрана.

## Тести: що перевіряємо

- Чисті функції — без DOM/мережі (`geo`, `targets`, `zones`, `simulation`).
- API — через підмінений `fetch`: URL, envelope, POST JSON, помилки.
- Store — через мок-режими й підмінені таймери: мерж за `id`, захист від старих `ts`, тривоги, потік.
- `App` — статичний рендер обох екранів і картки цілі; ловить регресії розмітки й пропсів.

## Свідомо не робилося

- Не додано авторизацію та справжній бекенд ARGUS — контракт описано в `docs/02-api-contract.md`.
- Не реалізовано історію руху (треки як смужки) — це наступний етап розвитку.
- Не додано React Router, React Query, глобальний Context — для двох екранів і двох store зайва інфраструктура.
- `window.argus` існує лише для ручного налагодження; UI від нього не залежить.
